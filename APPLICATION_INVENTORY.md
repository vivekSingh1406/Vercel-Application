# Historical source inventory and current migration mapping

Inspected the complete `src/` tree, package/build/TypeScript configuration, assets, existing review scripts, and content documentation before implementation. The source was inspected before conversion; the Angular project has since been removed at the user’s request. Source paths below document that historical inventory.

## Application shape and dependencies

Angular 22 standalone application: `main.ts` bootstraps `App` with router and global error listeners; no NgModule, guards, interceptors, environment files, HTTP client, custom pipes, authentication, external API, table widget, pagination, or manual sort control exists. Dependencies are Angular common/compiler/core/forms/platform-browser/router, RxJS and tslib. Development uses Angular CLI/build, TypeScript, Prettier and Playwright. No Bootstrap, Material, PrimeNG, Font Awesome, chart/date library, or external font exists. DatePipe is the sole formatting pipe. Custom inline SVG icons and native HTML dialogs supply the UI. `styles.scss` contains plain CSS (2,830 lines), six palettes, responsive rules and reduced-motion behavior. App SCSS is empty. All six MP4 files, original JPEG, six extracted posters and favicons must be retained.

## Models and persistence decisions

- Message: id, message, authorOfMessage, createdAt → community_message.
- Blog: id, title, slug, excerpt, content, author, optional image/category, createdAt → story.
- BlogSubmission extends Blog with optional imageName → story with DRAFT status; publishing changes status atomically, preserving ID/date/image.
- GalleryItem: id/src/title/alt/category/credit → static/data/media.json (gallery array), loaded as a plain DTO; no database table.
- VillageVideo: id/title/description/src/poster/duration/credit → static/data/media.json (videos array), loaded as a plain DTO; no database table.
- Theme: id/name/swatch → static configuration; no table.
- Village/site copy, navigation, form limits and theme palettes remain configuration/presentation assets. No artificial user/category relationship is invented. Authors are free text in the original.

## All data sources

`blogs.ts`: three starter editorial stories. `messages.ts`: three labeled editorial welcome notes. `gallery.ts`: six records. `videos.ts`: six records. Stories/messages become MySQL Flyway seed data; gallery/video records remain static JSON. `village-info.ts`: all editorial page copy and section values; preserved in a configuration JSON resource. `themes.ts`: six palette descriptions. `site-config.ts`: names/location/copy, WhatsApp number, limits, empty social links, five nav links. No separate mock JSON or sessionStorage exists.

localStorage keys: `gautiyan-tola-blogs`, `gautiyan-tola-messages`, `gautiyan-tola-submissions` become database-backed collections; `gautiyan-tola-theme` stays device-local. Existing personal browser records are not accessible from the repository; retain original export capability and document migration boundary. Temporary UI arrays/signals (tabs, filters, modal selection, pending deletion, form state) remain browser state.

## Architecture and route mapping

Java 17 / Spring Boot / MVC / JSP + JSTL / Maven executable WAR / JPA + Hibernate / Flyway / MySQL as the database. Gallery/video metadata and files remain static; uploaded story images live on disk with URLs in MySQL. Executable WAR is chosen because Spring Boot supports JSP with WAR, not executable JAR packaging (https://docs.spring.io/spring-boot/reference/web/servlet.html). Controllers bind validated DTOs; services own business rules; repositories own database access; JSP renders escaped model content. Fetch is used for forms/editors only to preserve no-reload modal and success interactions; HTML form endpoints remain MVC endpoints. Search/filter operate on rendered database data, preserving immediate behavior.

## Necessary semantic differences

Database persistence is shared, so obsolete claims about local-only saving/rebuilding must change while keeping layout and workflow. Drafts still require review; WhatsApp is still a separate user-confirmed step. Original admin has no authorization: preserve open workspace for local use and bind localhost by default; an optional authenticated deployment mode can protect management without inventing an account-registration workflow. No automatic public deployment or external messages are part of this migration.
